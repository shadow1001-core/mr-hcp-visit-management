# 医药代表学术拜访管理子系统：业务规则

## 1. 文档目的

本文档定义本项目 MVP 的核心业务规则、状态转换、合规边界和月度看板统计口径。后续数据库 Schema、API、前端交互和测试用例均应以本文档为准。

## 2. 术语

| 术语 | 英文/标识 | 定义 |
| --- | --- | --- |
| 医药代表 | MR | 创建拜访计划并执行签到、学术沟通、签退和记录反馈的人员。MVP 不实现 MR 的登录和权限控制。 |
| 医生 | HCP | 接受学术沟通的医疗专业人员。 |
| 医院 | Hospital | 拜访发生的目标地点，保存用于距离校验的标准经纬度。 |
| 产品 | Product | 本次拜访计划沟通的药品或学术产品。一次拜访可以关联一个或多个产品。 |
| 拜访计划 | Visit Plan | MR 在实际到访前创建的记录，包含目标 HCP、医院、科室、计划时间和目标产品。 |
| 实际拜访 | Actual Visit | 拜访计划完成首次签到后形成的实际执行记录。一个计划最多产生一次实际拜访。 |
| 签到 | Check-in | MR 到达医院后提交当前位置，由服务端记录实际签到时间并校验与医院的距离。 |
| 签退 | Check-out | MR 完成沟通后提交当前位置，由服务端记录实际签退时间、计算停留时长并完成剩余合规校验。 |
| 拜访记录 | Call Report | 签退后提交的完整反馈，包括谈话要点、HCP 反馈、学术沟通内容和资料派发情况。 |
| 目标产品 | Target Product | 创建计划时指定的产品集合，至少包含一个产品，同一产品在集合中只能出现一次。 |
| 异常原因 | Compliance Finding | 由某一条合规规则产生的结构化异常。一次拜访可以同时存在多个异常原因。 |
| 业务时区 | Business Time Zone | 用于前端显示和月度归属计算的配置时区；数据库仍统一存储 UTC 时间。 |

## 3. 状态机

### 3.1 状态定义

| 状态 | 含义 | 允许的下一业务操作 |
| --- | --- | --- |
| `PLANNED` | 已创建拜访计划，尚未签到 | 签到 |
| `CHECKED_IN` | 已完成签到，实际拜访进行中 | 签退 |
| `CHECKED_OUT` | 已完成签退，等待首次提交完整拜访记录 | 提交拜访记录 |
| `REPORTED` | 已提交完整拜访记录，拜访流程结束 | 整体更新报告（状态不变） |

### 3.2 状态流转

```text
PLANNED --签到--> CHECKED_IN --签退--> CHECKED_OUT --提交拜访记录--> REPORTED
REPORTED --整体更新报告--> REPORTED
```

### 3.3 状态约束

- 状态只能按上述顺序单向推进，不允许跳过、回退或重新开始。
- 只有 `PLANNED` 状态可以签到。
- 只有 `CHECKED_IN` 状态可以签退。
- 只有 `CHECKED_OUT` 状态可以首次提交完整拜访记录。
- `REPORTED` 是本次 MVP 的终态。
- `REPORTED` 可以整体更新当前报告，但该操作不产生新的生命周期状态。
- 合规异常不会阻止状态推进；生命周期状态与是否异常是两个独立维度。
- 非法或重复操作必须返回明确的业务错误，并保持原状态和原始数据不变。

## 4. 编号业务规则

### 4.1 计划与实际拜访

- **BR-001**：每个拜访必须先创建计划；MVP 不支持无计划拜访。
- **BR-002**：一个拜访计划最多对应一次实际拜访。
- **BR-003**：计划首次成功签到后视为已产生实际拜访；未签到的 `PLANNED` 记录不属于实际拜访。
- **BR-004**：创建计划时必须指定至少一个目标产品。
- **BR-005**：一次拜访可以关联一个或多个目标产品。
- **BR-006**：同一产品在同一次拜访的目标产品集合中只能出现一次；重复产品输入必须被拒绝，且数据库层应保证唯一性。

### 4.2 签到与签退

- **BR-007**：只有 `PLANNED` 拜访可以签到；成功后状态变为 `CHECKED_IN`。
- **BR-008**：签到坐标由客户端输入，签到时间由服务端生成，客户端不能指定或覆盖签到时间。
- **BR-009**：签到时必须计算签到坐标与医院标准坐标的距离，并记录对应结果。
- **BR-010**：只有 `CHECKED_IN` 拜访可以签退；成功后状态变为 `CHECKED_OUT`。
- **BR-011**：签退坐标由客户端输入，签退时间由服务端生成，客户端不能指定或覆盖签退时间。
- **BR-012**：签退时必须计算签退坐标与医院标准坐标的距离。
- **BR-013**：停留时长由服务端使用实际签退时间减去实际签到时间计算，客户端不能提交或覆盖。
- **BR-014**：对已经成功签到的拜访再次签到，必须返回明确的重复签到业务错误，不得覆盖首次签到时间、坐标或距离数据。
- **BR-015**：对已经成功签退的拜访再次签退，必须返回明确的重复签退业务错误，不得覆盖首次签退时间、坐标、距离、停留时长或异常结果。

### 4.3 拜访记录

- **BR-016**：只有 `CHECKED_OUT` 拜访可以首次提交完整拜访记录。
- **BR-017**：首次提交成功后，状态变为 `REPORTED`。
- **BR-018**：完整拜访记录至少应覆盖谈话要点、HCP 反馈、学术沟通内容和资料派发情况。

### 4.4 合规校验

- **BR-019**：实际停留时长小于 5 分钟时，产生“停留时长不足”异常。
- **BR-020**：签到位置与医院标准位置的距离大于 500 米时，产生“签到位置偏离”异常。
- **BR-021**：签退位置与医院标准位置的距离大于 500 米时，产生“签退位置偏离”异常。
- **BR-022**：一次拜访可以同时保存多个异常原因，后产生的异常不得覆盖已有异常。
- **BR-023**：异常拜访仍可以正常签退和提交拜访记录；异常只影响合规结论，不改变生命周期流转。

### 4.5 时间

- **BR-024**：数据库中的计划时间、签到时间、签退时间和记录时间统一以 UTC 存储。
- **BR-025**：API 中的时间值应携带明确时区信息，禁止使用无法确定时区的时间值。
- **BR-026**：前端按照配置的业务时区显示时间。
- **BR-027**：月度统计边界按照业务时区的自然月确定，再转换为 UTC 时间范围执行查询。

### 4.6 月度统计

- **BR-028**：月度看板以实际签到时间所属的业务时区自然月作为月份归属。
- **BR-029**：只有已经成功签到的实际拜访才计入看板，即纳入 `CHECKED_IN`、`CHECKED_OUT` 和 `REPORTED` 状态。
- **BR-030**：`PLANNED` 状态不计入看板。
- **BR-031**：异常拜访仍计入总拜访次数，并单独计入异常拜访次数。
- **BR-032**：同一次拜访中的同一产品最多增加一次该产品的拜访计数。
- **BR-033**：一次多产品拜访分别为每个关联产品增加一次拜访计数。
- **BR-034**：同一次拜访即使存在多个异常原因，在同一产品下也最多增加一次异常拜访计数。
- **BR-035**：已经签到但尚未签退的拜访计入总数；其签到位置异常可以计入异常次数，但最终合规结论要到签退后才能完整确定。

### 4.7 报告更新

- **BR-036**：`REPORTED` 状态允许通过同一个 PUT 接口整体替换报告内容，但不得修改签到、签退、停留时长或合规异常。
- **BR-037**：报告至少包含一个实际沟通产品；实际沟通产品必须是计划目标产品且不得重复。
- **BR-038**：资料数量必须是非负整数；报告及其沟通、资料子项必须在一个事务中创建或整体替换。

## 5. 边界定义

### 5.1 停留时长

- 5 分钟按 **300 秒**定义。
- 使用服务端时间戳的精确差值执行判断，不能使用页面展示时四舍五入后的分钟数。
- `停留时长 < 300 秒`：异常。
- `停留时长 = 300 秒`：正常。
- `停留时长 > 300 秒`：正常。

### 5.2 地点距离

- 经纬度使用 WGS 84 坐标。
- MVP 统一使用 Haversine 大圆距离计算，单位为米。
- 合规判断使用未四舍五入的原始计算结果；四舍五入仅用于界面展示。
- `距离 > 500 米`：异常。
- `距离 = 500 米`：正常。
- `距离 < 500 米`：正常。
- 签到和签退分别判断，任一阶段超过阈值都会产生对应异常原因。

### 5.3 重复操作

- 重复签到和重复签退是状态冲突，不是新的业务事件。
- 重复请求不得更新时间、坐标、距离、停留时长或异常原因。
- API 设计阶段应为两类冲突定义稳定、可识别的业务错误码；HTTP 层建议映射为 `409 Conflict`。

## 6. 月度看板统计口径

### 6.1 月份归属

- 按 **BR-028**，以实际签到时间所属月份作为拜访的统计月份。
- 月份归属按照配置的业务时区计算，不使用计划时间或签退时间。
- 例如，先确定业务时区下 `[当月第一天 00:00:00, 下月第一天 00:00:00)` 的半开区间，再转换为 UTC 查询范围。

### 6.2 纳入范围

- 按 **BR-029**，状态为 `CHECKED_IN`、`CHECKED_OUT` 或 `REPORTED` 的拜访均计入。
- 按 **BR-030**，状态为 `PLANNED` 的拜访不计入。
- 按 **BR-031**，异常拜访仍计入总拜访次数。
- 按 **BR-035**，已签到但尚未签退的拜访尚未完成时长和签退距离校验，因此其最终合规结论仍可能变化。

### 6.3 产品维度计数

- 一次拜访关联某个产品时，为该产品增加一次拜访计数。
- 按 **BR-032**，同一次拜访中的同一产品最多计数一次。
- 按 **BR-033**，一次多产品拜访会分别为每个关联产品增加一次计数。
- 因此，各产品拜访次数之和可能大于去重后的实际拜访总数；两者不是同一指标。

### 6.4 异常次数

- 看板至少提供产品维度的总拜访次数和异常拜访次数。
- 某次拜访只要存在至少一个异常原因，即在它关联的每个产品下分别增加一次异常拜访计数。
- 按 **BR-034**，同一次拜访即使有多个异常原因，在同一产品下的异常拜访次数仍只增加一次。
- 按 **BR-035**，`CHECKED_IN` 拜访如果签到距离已经触发异常，应计入异常次数；如果尚无已确定异常，其合规校验仍处于未完成状态。

## 7. 本次 MVP 不实现的功能

- 无计划拜访。
- 一个计划产生多次实际拜访。
- 完整的用户登录、身份认证、角色权限和数据权限。
- 拜访计划审批流程。
- 地图 SDK、地图选点、轨迹展示和真实移动端 GPS 自动采集。
- 图片、PPT、文献或其他附件的文件上传与管理。
- GPS 防作弊、人脸识别、医生电子签名等真实性增强能力。
- 离线签到、离线签退和断网补传。
- 计划改期、取消、周期计划和批量创建。
- `REPORTED` 后带审批和版本历史的正式更正流程；MVP 仅支持当前报告的整体替换。
- 与外部 CRM、主数据、消息通知或地图服务的集成。
